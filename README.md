# TripGo - лабораторные работы

## Запуск проекта

Из корня репозитория выполнить:

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

Применить миграции базы данных:

```bash
make migrate
```

Запустить сервис:

```bash
make run
```

## Конфигурация

Основные переменные окружения:

| Переменная | Назначение |
|---|---|
| `HTTP_ADDR` | Адрес HTTP-сервера |
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `LOG_LEVEL` | Уровень логирования |
| `SHUTDOWN_TIMEOUT` | Таймаут graceful shutdown |
| `DATABASE_MAX_CONNS` | Максимальное количество соединений с БД |
| `DATABASE_MIN_CONNS` | Минимальное количество соединений с БД |
| `DATABASE_CONNECT_TIMEOUT` | Таймаут подключения к БД |
| `DATABASE_QUERY_TIMEOUT` | Таймаут выполнения запросов |
| `DATABASE_MAX_CONN_LIFETIME` | Максимальное время жизни соединения |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Адрес OpenTelemetry Collector |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | Протокол экспорта телеметрии |
| `OTEL_TRACES_SAMPLER` | Стратегия семплирования трассировок |
| `OTEL_EXPORTER_OTLP_INSECURE` | Использование OTLP без TLS |

Фактические значения задаются в локальном окружении. Не добавляйте секреты и реальные учётные данные в репозиторий

## Архитектура

Приложение разделено на слои. HTTP-слой принимает запросы и вызывает сценарии приложения, use case координируют операции, а инфраструктурные компоненты обеспечивают работу с PostgreSQL и телеметрией

### Слои приложения

- `internal/domain` - доменная модель, правила и ошибки предметной области
- `internal/model` - структуры данных, используемые между компонентами приложения
- `internal/usecase` - сценарии создания, завершения и получения поездок
- `internal/repository` - реализация операций чтения и записи поездок в PostgreSQL
- `internal/postgres` - создание и настройка пула соединений с PostgreSQL
- `internal/txmanager` - управление транзакциями и предоставление транзакционного исполнителя через контекст
- `internal/http` - HTTP-обработчики и преобразование доменных ошибок в HTTP-ответы
- `internal/httpserver` - HTTP-сервер и middleware для логирования, метрик, обработки паник и инструментирования запросов
- `internal/observability` - настройка OpenTelemetry и бизнес-метрик
- `internal/config` - загрузка конфигурации приложения

### Направление зависимостей

HTTP-обработчики вызывают use case через интерфейсы. Сценарии приложения используют необходимые им контракты репозитория и транзакционного менеджера. Репозиторий работает с PostgreSQL через инфраструктурные компоненты

Доменный слой не должен зависеть от HTTP или PostgreSQL. Это позволяет тестировать бизнес-правила отдельно от транспорта и хранения данных

### Интерфейсы и причины их расположения

Интерфейсы объявлены в нескольких пакетах на границах взаимодействия компонентов:

- `internal/http/trip/create/contract.go` - интерфейс `TripCreator`, используемый HTTP-слоем для вызова сценария создания поездки
- `internal/usecase/trip/create/contract.go` - контракты репозитория и транзакционного менеджера для сценария создания поездки
- `internal/usecase/trip/finish/contract.go` - контракты репозитория и транзакционного менеджера для завершения поездки
- `internal/usecase/trip/get/contract.go` - контракт репозитория для получения поездки
- `internal/txmanager/txmanager.go` - публичный интерфейс `TxManager` и его реализация

Такое разделение позволяет use case зависеть от требуемого поведения, а не от конкретной реализации PostgreSQL. Это упрощает модульное тестирование с mock-объектами и уменьшает связанность компонентов

### Транзакционная граница

При создании поездки запись самой поездки и запись истории её статусов выполняются в одной транзакции. При завершении поездки изменение её состояния и добавление записи в историю также выполняются в одной транзакции

Если одна из операций завершается ошибкой, транзакция не фиксируется. Это предотвращает сохранение только части связанных изменений

### Уровень изоляции

Используется уровень изоляции `Read Committed`

Запрет двух активных поездок у одного водителя обеспечивается уникальным частичным индексом `trips_limitation_for_driver_idx` в PostgreSQL
Ограничение на уровне базы данных защищает от конкурентных запросов, которые иначе могли бы одновременно создать несколько активных поездок для одного водителя

Нарушение этого ограничения распознаётся в `internal/repository/trip.go` по коду PostgreSQL `23505` и имени индекса. Ошибка преобразуется в доменную ошибку `ErrDriverBusy`, которая на HTTP-уровне представляется ответом `409 Conflict` с кодом `driver_busy`

### Менеджер транзакций

Интерфейс `TxManager` объявлен в `internal/txmanager/txmanager.go`:

```go
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}
```

Метод `Do` начинает транзакцию и передаёт её через контекст функции `fn`. Если функция завершается успешно, менеджер выполняет `COMMIT`. Если функция возвращает ошибку, транзакция не фиксируется и выполняется `ROLLBACK`. При панике отложенный вызов отката выполняется, после чего паника продолжает распространяться

Если в контексте уже есть транзакция, вложенный вызов `Do` использует её вместо открытия новой

## Обработка ошибок

Доменная логика не зависит от HTTP-статусов. Ошибки предметной области определяются в доменном слое, а HTTP-слой преобразует их в соответствующие ответы API

Обработчики используют единый формат ошибок через пакет `internal/http/domainerror`. В частности, конфликт активной поездки возвращается как `409 Conflict` с кодом `driver_busy`

## Проверка работоспособности

- `GET /health` проверяет работоспособность процесса и возвращает `200 OK`, если обработчик доступен
- `GET /ready` проверяет готовность сервиса, включая доступность PostgreSQL, и возвращает `503 Service Unavailable`, если база данных недоступна

При получении `SIGINT` или `SIGTERM` сервер выполняет graceful shutdown с ограничением времени из `SHUTDOWN_TIMEOUT`

## Observability

Для трассировок, метрик и корреляции логов используется OpenTelemetry

### Трассировки

HTTP-запросы инструментируются для сбора трассировок. Операции с PostgreSQL могут отображаться как дочерние spans соответствующего HTTP-запроса

Трассировки можно просматривать в Jaeger. Для проверки создания поездки отправьте запрос через API и найдите trace, соответствующий запросу `POST /api/v1/trips`

### Метрики

Сервис собирает HTTP-метрики и бизнес-метрики, включая:

- `http.server.request.duration` - длительность HTTP-запросов.
- `http.server.active_requests` - количество активных запросов.
- `tripgo.trips.created` - количество успешно созданных поездок.
- `tripgo.trips.completed` - количество успешно завершённых поездок.

В Prometheus метрики могут отображаться с нормализованными именами, например `tripgo_trips_created_total`.


### Структурированные логи

HTTP-логи содержат метод запроса, маршрут, HTTP-статус, длительность, `trace_id` и `span_id`. Это позволяет связать запись лога с соответствующей трассировкой в Jaeger

### Работа без Collector

Сервис должен запускаться и обслуживать HTTP-запросы даже при недоступном OpenTelemetry Collector. В таком случае экспорт телеметрии может не выполняться, но запуск приложения не должен зависеть от доступности Collector
